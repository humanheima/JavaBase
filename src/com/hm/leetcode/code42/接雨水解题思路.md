# LeetCode 42. 接雨水（Trapping Rain Water）解题文档

## 一、题目描述

给定 `n` 个非负整数表示每个宽度为 1 的柱子的高度图，计算按此排列的柱子，下雨之后能接多少雨水。

**示例：**

| 输入 | 输出 | 说明 |
|------|------|------|
| `[0,1,0,2,1,0,1,3,2,1,2,1]` | `6` | 经典图示，凹槽共接 6 单位水 |
| `[4,2,0,3,2,5]` | `9` | 左右高、中间低，接 9 单位水 |
| `[3,3,3]` | `0` | 没有凹陷，接不到水 |

**链接：** https://leetcode.cn/problems/trapping-rain-water/

---

## 二、核心观察

1. **逐格累加**：把总水量拆成「每一根柱子上方能积多少水」之和，而不是整片去算。
2. **木桶原理**：位置 `i` 能积的水高由**左侧最高**和**右侧最高**中**较矮**的那个决定：
   ```
   water[i] = min(leftMax[i], rightMax[i]) - height[i]   // 小于 0 视为 0
   ```
3. 所有优化解法（动规 / 双指针 / 单调栈），本质都是在**降低「求每个位置左右最高」的重复计算**。

---

## 三、四种解法

### 解法一：暴力枚举

**思路：** 对每个位置 `i`，分别向左、向右扫一遍求出两侧最高，套用 `min(leftMax, rightMax) - height[i]`。

```java
public static int trapBruteForce(int[] height) {
    int total = 0;
    for (int i = 1; i < height.length - 1; i++) {
        int leftMax = 0, rightMax = 0;
        for (int l = i; l >= 0; l--) leftMax = Math.max(leftMax, height[l]);
        for (int r = i; r < height.length; r++) rightMax = Math.max(rightMax, height[r]);
        total += Math.min(leftMax, rightMax) - height[i];
    }
    return total;
}
```

- **时间复杂度：** O(n²)
- **空间复杂度：** O(1)
- **优点：** 最贴合定义、最易理解
- **缺点：** 每个位置都重复扫两侧，数据大时超时

---

### 解法二：动态规划（空间换时间）

**思路：**
1. 用 `leftMax[i]` 记录 `[0, i]` 的最高柱，正向递推。
2. 用 `rightMax[i]` 记录 `[i, n-1]` 的最高柱，反向递推。
3. 再遍历一次，逐格累加 `min(leftMax[i], rightMax[i]) - height[i]`。

```java
leftMax[0] = height[0];
for (int i = 1; i < n; i++) leftMax[i] = Math.max(leftMax[i - 1], height[i]);
rightMax[n - 1] = height[n - 1];
for (int i = n - 2; i >= 0; i--) rightMax[i] = Math.max(rightMax[i + 1], height[i]);
for (int i = 0; i < n; i++) total += Math.min(leftMax[i], rightMax[i]) - height[i];
```

- **时间复杂度：** O(n)
- **空间复杂度：** O(n)
- **优点：** 思路直接，把暴力的重复扫描预处理掉
- **缺点：** 需要两个额外数组

---

### 解法三：双指针（最优）

**思路：** 把动规的两个数组省成两个变量。左右指针向中间收缩，同时维护 `leftMax`、`rightMax`：
- **谁那侧的「已知最高」更矮，谁的当前格水量就已经确定**——因为另一侧存在一个更高的墙兜底，较矮侧就是瓶颈。
- 据此移动较矮的一侧指针并结算水量。

```java
int left = 0, right = height.length - 1, leftMax = 0, rightMax = 0, total = 0;
while (left < right) {
    leftMax = Math.max(leftMax, height[left]);
    rightMax = Math.max(rightMax, height[right]);
    if (leftMax < rightMax) {
        total += leftMax - height[left];
        left++;
    } else {
        total += rightMax - height[right];
        right--;
    }
}
```

- **时间复杂度：** O(n)
- **空间复杂度：** O(1)
- **优点：** 一次遍历、常数空间，综合最优
- **缺点：** 「为什么较矮侧能确定」需要想通，不如动规直观

> **细节 1：最左、最右两格的水量恒为 0**
> 接水靠两侧有更高的「墙」挡着。最左柱左边没有任何柱子（没有左墙），水直接流走；最右柱同理。没有一侧边界就兜不住水，所以首尾两格恒为 0——这也是暴力解法循环从 `i = 1` 到 `i < length - 1`、跳过首尾的原因。
> 双指针虽未显式跳过，但算出来自然是 0：位置 0 被结算时 `leftMax` 必等于 `height[0]` 本身（左边再无柱子可比），贡献 `leftMax - height[0] = 0`；最右端对称。

> **细节 2：为什么循环条件是 `left < right` 而不是 `left <= right`**
> 可以证明两指针最终**相遇在全局最高柱**处：每次移动较矮一侧，在任一指针到达最高柱前，那侧的 max 都不会超过最高柱，于是较矮侧不断向它收缩，最终汇聚于此。而最高柱上方接不到水（`min(左max, 右max) - 自身高度`，自身最高 → 结果 0），所以相遇那一格无需处理。
> 若改成 `left <= right`：相遇时 `left == right == 最高柱`，`leftMax`、`rightMax` 都会更新为该柱高度，`total += 高度 - 高度 = 0`——加了个 0，结果不变，纯属多跑一次迭代。选 `<` 更干净，也避免误以为相遇格可能有水。
>
> **用例验证** `[4,2,0,3,2,5]`（最高柱是末尾的 `5`）：
>
> | left | right | leftMax | rightMax | 结算 | 指针移动 | total |
> |------|-------|---------|----------|------|----------|-------|
> | 0 | 5 | 4 | 5 | 4−4=0 | left→1 | 0 |
> | 1 | 5 | 4 | 5 | 4−2=2 | left→2 | 2 |
> | 2 | 5 | 4 | 5 | 4−0=4 | left→3 | 6 |
> | 3 | 5 | 4 | 5 | 4−3=1 | left→4 | 7 |
> | 4 | 5 | 4 | 5 | 4−2=2 | left→5 | 9 |
> | 5 | 5 | — | — | 相遇停止 | — | **9** ✓ |
>
> 指针恰好相遇在 index 5（高度 5，全局最高），这一格本就盛水 0，无需结算。

### 解法四：单调栈

**思路：** 维护一个**高度递减**的下标栈，按「凹槽」横向分层结算：
1. 当前柱子比栈顶高时，弹出栈顶作为**凹槽底** `bottom`。
2. 此时新的栈顶是**左边界** `left`，当前柱子是**右边界** `i`。
3. 该层水量 = 宽度 `(i - left - 1)` × 高度 `(min(height[left], height[i]) - height[bottom])`。
4. 循环结算，直到当前柱子不再高于栈顶，再入栈。

```java
Deque<Integer> stack = new LinkedList<>();
for (int i = 0; i < height.length; i++) {
    while (!stack.isEmpty() && height[i] > height[stack.peek()]) {
        int bottom = stack.pop();
        if (stack.isEmpty()) break;
        int left = stack.peek();
        int width = i - left - 1;
        int boundedHeight = Math.min(height[left], height[i]) - height[bottom];
        total += width * boundedHeight;
    }
    stack.push(i);
}
```

- **时间复杂度：** O(n)，每个下标至多进出栈一次
- **空间复杂度：** O(n)
- **优点：** 提供「横向按层」的独特视角，是栈类题型的经典模板
- **缺点：** 逻辑较绕，弹栈后要判空、宽高计算易错

## 四、四种解法对比

| 解法 | 核心思路 | 时间 | 空间 | 优点 | 缺点 |
|------|----------|------|------|------|------|
| 一、暴力 | 每格现场扫两侧最高 | O(n²) | O(1) | 最直观 | 会超时 |
| 二、动态规划 | 预处理左右最高数组 | O(n) | O(n) | 直接高效 | 占额外空间 |
| 三、双指针 | 两端收缩、较矮侧结算 | O(n) | O(1) | 综合最优 | 思路要想通 |
| 四、单调栈 | 递减栈横向按层结算 | O(n) | O(n) | 视角独特 | 易错 |

---

## 五、易错点总结

1. **边界格不接水**：第一根和最后一根柱子两侧无墙，接不到水（暴力解法循环从 `1` 到 `n-2`）。
2. **空数组 / 长度 < 3**：动规要先判 `n == 0`；柱子数少于 3 时结果必为 0。
3. **双指针移动条件**：必须移动 `leftMax`、`rightMax` 中**较矮**的一侧，移错方向会少算或多算。
4. **单调栈弹栈后判空**：弹出 `bottom` 后若栈空，说明左边没有边界，直接 `break`，否则会用错误的 `left`。
5. **「纵向逐格」vs「横向分层」**：前三种按列累加，单调栈按行累加，两套思路不要混用。
